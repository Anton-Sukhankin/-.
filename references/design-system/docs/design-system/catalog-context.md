## Короткий путь из нового контекста

Команды ниже запускаются из корня рабочей копии. Поддерживается Python 3; режим -B не создаёт новых pycache. Для PowerShell доступны find-design-context.ps1 и read-context.ps1 с явным PythonExecutable.

1. Установить задачу и данные у владельцев Каталога. Выбрать библиотеку через source-blocks.json. Для основной библиотеки: python -B scripts/find_design_context.py "v-input" --file DS-01 --kind component --limit 8. Не выбирать первый результат автоматически: варианты поля даты не заменяют обычное текстовое поле. Для него точный маршрут — DS-01:component:418:2000.
2. Из результата взять точный ID, card, requiredContext, статус и источник. Запрос деталей: python -B scripts/find_design_context.py "DS-01:component:418:2000" --details --limit 1. Для нужного состояния добавить --property "state=invalid" --property "size=S - 40 px"; это пример технической проверки, не назначение состояния интерфейсу.
3. Карточку читать адресно: python -B scripts/read_context.py docs/design-system/figma-workflow.md --headings; затем --section "Сборка интерфейсов из компонентов" --limit 6000. hasMore требует следующего --offset; усечённый вывод не принимается за весь контракт.
4. Прочитать обязательные зависимости выбранной карточки; для составного DS-02 выбрать --node/--property и --dependency-details, не подгружать весь архив. Техническая проверка инструмента на карточке квартиры не делает её частью навигатора.
5. Открыть сохранённый оригинальный PNG и актуальный Figma file/node. Сверить component key набора и нужного варианта, defaultVariant, свойства, связанные вложения и токены. Публикацию и успешный импорт в целевой файл подтверждать отдельно.
6. Применить выбор способа сборки: готовый инстанс, самостоятельные инстансы в проектном контейнере или настройка вложений составного инстанса — по фактической анатомии, без автоматического усложнения.
7. Проверить данные и состояния, обе оси размеров, длинный текст и граничное содержимое в полном контексте. Прототипное поведение проверять отдельно от статических экспортов. Передать координатору источники, новые узлы и конкретные ограничения.

Сохранённые карточки v-input и v-button имеют review=stale: их текущий исходник обязательно перепроверяется исполнителем Figma. У иконок поиск search возвращает также старый Pack 1; самостоятельная системная Search имеет маршрут DS-03:component:2525:1025. Детали набора по умолчанию могут вернуть другую иконку, поэтому выбирайте точный node/свойства. Нулевой результат кратких запросов modal/search по DS-01 не доказывает отсутствия подходящей композиции; не придумывайте готовый компонент по названию.

## Инструменты и проверка

- Поиск использует локальный catalog.json и сохранённые evidence, не путь к «Продажам».
- scripts/read_context.py локализован из общего инструмента исходного проекта; точное происхождение сохранено в реестре внешних зависимостей.
- python -B scripts/validate_design_docs.py проверяет JSON, локальные ссылки, идентичность реестров/компонентов и PNG. По умолчанию пишет результат вне рабочей копии, в «Проверки переноса ／ Transfer checks/Рабочие проверки ／ Working checks».
- Проверка бронирования не входит в рабочую проверку DS Каталога. Отдельный --historical-booking-root возможен только при явном исследовании исходного исторического контекста.
- Генераторы существующего пакета сохранены. Перенос не меняет источник фактов, поэтому catalog/source-blocks/contracts/images не регенерируются ради нового пути.
- Приёмка документации и реальное применение в Figma независимы. Не заявлять импорт по наличию ключа, поведение по PNG или полный целевой навигатор по одной проверочной композиции.

## История и внешние материалы

Исходные parent README/AGENTS/«Правила работы с контекстом» Продаж не являются инструкциями рабочей копии. Вместо них действуют AGENTS рабочей копии, обёртки и владельцы Каталога.

Внешние ссылки исторических исследований ведут по явно отмеченным исходным адресам. Они не нужны поиску, чтению и основной валидации. Классификация и происхождение. Полный исходный срез находится в соседней папке, его содержимое неизменно и его AGENTS/планы неактивны.

## Обновление копии

1. Зафиксировать новую версию/срез источника отдельно; прежний snapshot не перезаписывать.
2. Сравнить пути, типы, основные и именованные потоки, хеши и метаданные; классифицировать изменения библиотеки и локальной адаптации.
3. Применять обновления к working через владельца и штатные генераторы там, где меняются их источники. Исторический статус не повышать автоматически.
4. Перенести местные адаптации по явному журналу, проверить затронутые карточки, зависимости и потребителей.
5. Повторить механические проверки и адресный маршрут. При изменении компонента отдельно перепроверить его применение в Figma.
6. Сохранить полный diff working против выбранного snapshot и результаты независимой приёмки.

Текущий полный diff, собственные доказательства и команды хранятся вне working, в подпапке «Приёмка документации ／ Documentation review» проверок переноса.

Результат адаптации и доказательства · проверенный короткий маршрут. Самопроверка документатора не заменяет независимую приёмку и проверку применения в Figma.
